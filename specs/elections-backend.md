# Desired user behavior

The Elections feed shows candidates for the user's House district and Senate races, with concise policy positions grounded in campaign websites. Entering Elections starts a geography-scoped background build and saves normalized results so later reads reuse them. FEC registration is not proof of ballot access; do not present this as a definitive ballot. Loading, no available positions, and failed processing must be distinguishable. Source links and retrieval dates accompany positions.

- [x] Implement AI-assisted website discovery using each matched FEC candidate's name, office, state, district when applicable, and election year. OpenAI web search returns a likely candidate-site URL and retains its search sources as provenance; a source URL does not need to share the campaign site's domain. Page discovery reads `robots.txt`, follows a bounded number of sitemap indexes, and prioritizes relevant pages listed on the proposed site or its `www` alias. If no relevant sitemap pages are available, OpenAI web search is restricted to the proposed campaign domain and uses a site-qualified query with common policy-page titles and paths (including Key Issues and `/key-issues`) to find detail-page URLs. The server fetches only bounded pages on the proposed site or its `www` alias; it does not fetch the homepage or use navigation links as fallbacks. Sitemap and search-result titles/paths prioritize policy, issues, campaign promises, platform, and candidate/race pages. AI page inspection can mark a site `verified` when it supports the candidate and exact race, `ambiguous` when a likely campaign site was found but the pages don't fully state the race, or `rejected` when they conflict. An ambiguous page-inspection result is eligible only when discovery returned a valid campaign URL, approved same-site origins, and a current seven-day review window. Ambiguous search results without a validated URL remain ineligible. Missing sites and proposed records caused by fetch/search failures remain out. No separate corroborating source or manual review step is required. Run discovery explicitly with `node server/src/elections/cli.js --discover-sites --write --states WY --offices house`; defaults limit each run to 20 candidates and five pages per site. The command writes to the configured `DATABASE_URL`. Previous bounded live results are documented in [campaign-site search coverage](elections-campaign-site-search-coverage.json).

## 2. Crawl matched campaign sites with Crawlee

The crawler first uses sitemap URLs that indicate policy, issue, promise, platform, or related campaign-content pages. If none are listed, it uses domain-restricted web search to find relevant page URLs. It fetches only bounded URLs on approved campaign-site origins; it does not start at the homepage or expand HTML navigation links. Current `verified` and `ambiguous` sites with a URL, approved origins, and an active review window can be crawled. Sites without matching pages produce no crawl pages, so they contribute no positions. Extracted positions retain the existing allowed-topic and exact-source-excerpt checks before publication.

- [x] Implement a server-side crawler, bounded requests, public destination checks, text cleaning and saved source snapshots locally.
- [x] Verify a small live sample of actual campaign sites, including inaccessible and empty sites. It also exercised two live crawler edge cases: Vinson Watkins's proposed domain failed DNS resolution, and Jillian Balow's reachable site produced no policy-page URLs from sitemap/domain search. Both direct crawler calls returned no pages. The edge cases used temporary ambiguous-site fixtures and did not write to a database; they do not change the sites' stored review status. Results and rerun instructions are in [campaign-site search coverage](elections-campaign-site-search-coverage.json) and [the gated live acceptance test](../tests/elections-campaign-live-acceptance.test.mjs).

## On-demand feed builds

- [x] Implement request-triggered, idempotent feed-build jobs locally. On app entry, the mounted Elections panel requests a job for a verified House district and a shared state Senate job, even while another feed tab is selected. Census resolves geography; FEC supplies federal candidate discovery. If House geography is state-only, as currently in Missouri, no House job is created, while Senate remains available. Repeated roster, feed, and status requests reuse the unique scope row. The queue stores only derived state and district, never a street address. The client displays a preparation notice when Elections is selected and polls status every four seconds while work is queued or running.
- [x] Implement request-triggered Vercel processing for one geography job in Development and Preview. The API schedules queued House district and shared state Senate jobs with `waitUntil`, then returns the feed/status response while processing continues within the Vercel Function duration. Production dispatch is disabled. The worker claims only the requested job, renews its two-minute database lease, resumes completed stages after a retry, and saves the normalized results. A later status poll can reclaim an expired lease. The optional `npm.cmd --prefix server run elections:worker` command remains available for local processing. House FEC requests include the verified district; Senate work is state-scoped and shared by users in that state. FEC registration remains `unknown` for ballot status.
- [x] Persist normalized candidate evidence, campaign-site reviews, source snapshots, and validated position versions in the database. A completed scope stays cached and is not rebuilt on later reads; reads assemble the feed from those saved rows. Failed or partial stages become eligible for retry after 15 minutes when a later app request arrives. Existing published positions for the current site are skipped on retry, and earlier publications remain available if refresh work fails.
- [x] Apply and verify the three Elections migrations in `votefeed-dev` on 2026-10-28. Supabase recorded `20261028202229` (`elections_storage`), `20261028202239` (`election_discovery_observations`), and `20261028202247` (`election_feed_build_jobs`). All 19 expected Elections tables exist; the user geography foreign key is validated; the build-job table has RLS enabled, no DML privileges for `anon` or `authenticated`, and SELECT/INSERT/UPDATE/DELETE for `service_role`. The local migration filenames match the applied Development versions. Production was not changed.
- [ ] Deploy the Vercel API changes to Development and Preview environments that use `votefeed-dev`, then verify one House district and one state Senate job end to end through Preview. `server/vercel.json` sets a 300-second function duration for the API entrypoint. No Vercel deployment acceptance is claimed, and no candidate or campaign-position data has been imported by this on-demand process. Keep Production separate.
- [ ] Define the explicit refresh/invalidation policy for completed jobs. The initial behavior is build-once caching; completed jobs do not expire or rerun automatically.

No production deployment, import, or schedule is claimed. Existing local fixture evidence is documented in [elections-crawl.md](elections-crawl.md); its historical references to state discovery do not describe the current scope.
